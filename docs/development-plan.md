## 不可協商的核心（2026-08-28 定案）

> **1. 即時是硬需求。** 會後分析錄音不是這個產品——裁決只有在會議進行中才有意義。
>    「如果只是會後錄音那就不如不要做。」任何無法即時的路徑一律不列入選項。
>
> **2. 時程不是砍功能的理由。** 值得做的功能在時間壓力下仍做完，不以砍範圍換時程。
>    9/3 不是硬牆，核心能力做不完就延，不能為了趕上而降級成別的東西。

**這兩條推翻了先前一批「為了時程而妥協」的判斷。**
排程仍然要排（見下），但它的用途是**安排順序**，不是**決定砍什麼**。

## 排程的前提：瓶頸不是產能

全 AI 開發，**寫 code 的速度不是限制因素**，範圍可以開得比一般 8 天專案大。

**但有一件事不能被 AI coding 加速：**

> **調判斷品質的迭代輪數。**
> 每一輪都是「開一場真的會 → 看它介入得對不對 → 改判準 → 再開一場」。
> 每一輪都需要真人、真實時間、真實會議。**這是時間的函數，不是產能的函數。**

所以本方案的排程軸**不是天數，是「第幾次真實會議測試」**。

**推論**：既然產能不是瓶頸，最優策略是**盡早讓它能主持真會議，哪怕很粗糙**。
不要先花時間打磨架構——先讓它上場，用迭代輪數換品質。

## 二、系統架構

```
音訊 I/O 適配層
  ├─ 檔案回放      ← 開發測試，同一段錄音可反覆跑  ★ 最先做
  ├─ 本地多麥      ← demo 主線
  └─ Discord       ← 每人一軌（加分項）
        ↓ 每人一條音訊流 ＋ 誰在講話
   Pipecat 管線（VAD / SmartTurn / STT / TTS）
        ↓ 「誰、第幾秒、講了什麼」
┌──────────────────────────────────────┐
│           主席大腦（自己寫）            │
│                                      │
│  快路（規則，零延遲）                   │
│    計時器・沉默時長・發言佔比・回合計數    │
│                                      │
│  慢路（LLM，背景持續跑）                │
│    Inner Thoughts 評分（改造後）        │
│    Kaner 階段判斷                      │
│    候選發言預先生成 ← 延遲的解法         │
│                                      │
│  動態門檻 ＝ f(階段, 發言時長, 剩餘時間)  │
└──────────────────────────────────────┘
        ↓ 決定介入
   earcon ＋ TTS ＋ 螢幕視覺預告
```

**核心 agent 完全不知道自己在哪個平台**——這是適配層的意義。

## 三、範圍：做什麼、明確不做什麼

產能不是瓶頸，所以範圍可以開大——但**每加一項功能都要問「它會不會吃掉調品質的時間」**。

### P0 — 沒有就不成立

1. 音訊路徑：**檔案回放** ＋ **本地多麥**
2. **快路四種介入**：發言超時、議程超時、有人被冷落、僵局（回合計數）
3. **慢路兩種介入**：離題、假共識
4. **Kaner 三階段判斷** ← 差異化的根，沒有它整個定位落空
5. **earcon 打斷 ＋ TTS 發言**
6. **觀戰 UI** ← demo 的靈魂，讓評審看得到它在想什麼
7. **會議記錄（兩塊，缺一不可）**

   **A. 會議產出**（一般工具也有的）
   - 決議事項（誰、做什麼、何時前）
   - 待辦與負責人
   - **未解決事項，含 AI 的裁決理由**——「此題來回四輪無進展，判定延到下次，需要 X 數據」
   - 每個人的立場摘要

   **B. 主持記錄**（★ 這塊是我們獨有的）
   - 階段軌跡：幾分幾秒從發散進入呻吟區、幾分幾秒收斂
   - 每次介入的時間、類型、對象、**理由**
   - 發言時間分佈

   > 一般會議 AI 產出的是「**大家講了什麼**」，B 產出的是「**這場會議是怎麼被引導的**」。
   > demo 時把 B 打出來——「它每一次插話都有理由，而且理由可以被檢查」，
   > 比任何口頭解釋都有說服力。
   >
   > **B 幾乎是免費的**：這些資料觀戰 UI 本來就在顯示，只是寫成檔案。

### P1 — 產能允許，一併做

8. **主持風格檔位**（★ 零新增成本，優先做；依賴 P0#4 的動態門檻先完成）

   **決策（08-27）：不做「人格」，做「主持風格」。**

   | | 人格 | 主持風格 |
   |---|---|---|
   | 是什麼 | 這個 AI **是誰**（幽默／嚴肅／溫暖） | 它**怎麼行使權力**（強勢／溫和、快刀／耐心） |
   | 實作 | 新增一層 prompt 語氣控制 | **把既有參數包裝成檔位** |
   | 對定位 | 稀釋 | **強化** |

   **不做人格的三個理由**：
   1. 跟主席定位衝突——主席的權威來自中立與一致。有鮮明個性的主席，裁決會讓人覺得帶偏好
   2. 稀釋差異化——我們賣的是「管群體過程」，不是「一個有個性的聲音」
   3. 增加調校負擔，且可能干擾判斷（設定成幽默的人格可能在該嚴肅時開玩笑）

   **檔位就是既有參數（動態門檻、階段乘數）的組合**：
   - **嚴格主席**：打斷門檻低、時間管控嚴、快速推向裁決
   - **溫和引導**：門檻高、少打斷、多用提問把人帶進來
   - **效率優先**：收斂期乘數拉高，最短路徑到決議

   > **demo 價值**：現場切換風格，讓評審看到同一段會議在不同風格下的行為差異。
   > 這展示的是「背後真的有一個可控的模型」，而不是「prompt 裡寫了你是嚴格的主席」——
   > 剛好把差異化坐實。

   **聲音仍要選**：一個有權威感、中性、不做作的 TTS 聲音。這是必要的產品決策，但它不是人格設定。

   > 🔗 **與 #11 綁在一起做。** 檔位的附帶效果是**讓「調判斷品質」變得可測量**——
   > 見第七節。

9. **Discord 整合**：每人一軌，且團隊遠端也能測 → **直接增加迭代輪數，優先度比想像高**
10. 事實錯誤偵測、重複偵測（補滿介入類型表）
11. **介入品質的自動回放評估**：把歷次會議錄音存起來，改完判準後**重跑全部歷史會議**比較差異
    → 這一項是**用產能換迭代輪數**的唯一辦法，價值極高

### P2 — 看 Day 1 實測結果再決定

12. 小分類器取代部分 LLM 呼叫（延遲不夠時才做）

### 明確不做

- ✕ **視覺形象／avatar** → roadmap。複雜度不成比例，且真實會議的主席也不需要 avatar
- ✕ **人格設定** → 改做主持風格檔位（見 P1#8）
- ✕ Google Meet 官方 Media API（所有參與者都要加入 Developer Preview）。
  訪客路徑（AgentCall 那類）**可行但不做**，因為 demo 是實體會議 → roadmap
- ✕ 單麥 speaker diarization
- ✕ 任何微調／LoRA
- ✕ 多語言（只做中文）
- ✕ 議程設定 UI（用設定檔）
- ✕ 帳號系統、持久化、部署

## 七、第一順位風險

**不是**聽不聽得清楚（已繞過），**不是**打斷得自不自然（earcon 已解）。

> **是那套判斷準不準。**
> 打斷得再優雅，只要打斷錯人、時機不對，那個介入就是失敗的。

而且論文已經證實：**LLM 天生過度熱衷插話**。這是要主動對抗的內建偏差，不是調個參數就好。

→ 力氣配置：**平台與語音管線用最省事的方式做完，時間全部押在調判斷品質上。**

### 但「調品質」需要先有衡量方法，否則只能憑感覺調整

原本調參數只能靠感覺（「這次好像插太多」）。**P1#8 的風格檔位 ＋ P1#11 的歷史回放，合起來給出一個硬的驗證方法：**

```
拿同一場錄音 → 三個檔位各跑一次 → 比較行為差異
```

| 結果 | 代表什麼 |
|---|---|
| 差異符合預期（嚴格檔插得多、溫和檔插得少） | **模型真的被參數控制著** |
| 差異不明顯或方向錯亂 | **門檻設計沒有真的在起作用**——問題在架構，不在參數值 |

這比「感覺對不對」硬得多，而且**它驗的正好是第一順位風險本身**。

→ **#8 和 #11 要綁在一起做，不要拆開排。**
