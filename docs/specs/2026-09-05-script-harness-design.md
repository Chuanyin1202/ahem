# 腳本測試台設計（2026-09-05）

> **一句話**：與會者全是固定腳本，**只有主席是真的**——真的判斷、真的話術、真的
> Chair 時序。不接 Discord、不接麥克風、不接 STT。

## 為什麼要它

痛點是實際的：**開會湊不到人，環境也無法正常錄音**。而現有兩條路都不夠：

| 既有 | 給得了什麼 | 缺什麼 |
|---|---|---|
| `meeting_host.run <場景>` | 純文字輸入、瞬間跑完、真的快慢路判斷 | **不出聲**。沒有 Chair、沒有 earcon、沒有時機 |
| `meeting_host.live` | 全套真的 | 要 Discord、真人、安靜環境、能用的 STT |

要驗的是「主席在該出手的時候，用對的方式、對的時間點出手」——`run` 測不到出手，
`live` 每次都要湊人＋賭 STT。中間缺一條。

## 它的定位：無人值守的一路，不取代真人測試

**相對比較有效，絕對分數無效。** `docs/evaluation.md` 寫著：「絕對分數 3.8 沒意義；
同場景兩組參數的 3.8 vs 3.1 才有意義」。固定腳本正是它推薦的做法——同一份輸入
比較調參前後，這是這套東西最主要的價值。

**但要防過擬合腳本。** 腳本只量得到腳本裡有的形狀。2026-09-05 真實會議暴露的兩個
問題——STT 把環境噪音吐成逐字稿、房間只有一個人——第一個腳本永遠測不到（沒有 STT）。
所以：

> `experiments/holdout/` 的兩場真實會議留作回歸防線，**任何調參要兩邊都看**。
> 腳本分數變好不等於真實會議變好。

## 接縫在哪

只有兩個地方是假的，其餘一行不改。

```
                     ┌──────── 假 ────────┐        ┌────────── 真 ──────────┐
腳本（誰/第幾秒/講什麼）→ ScriptSource ──→ Session.consume() → 快路 / 慢路 / Chair
                                                                    ↓
                                                     LocalOutput（喇叭）
                                                  或 MutedOutput（無人值守）
```

**接縫 1：`ScriptSource.utterances()`**（`script_source.py`）
`Session.consume(pool)` 只依賴 `pool.utterances()`、`pool.offline()`，`MeetingBot`
另外會呼叫 `pool.feed()`。三個方法就是全部的契約。

⚠️ **必須逐秒吐 `Speaking`**，不能只在講完時吐 `Utterance`——快路的「發言超時」看的是
`state.speaking_now()`（partial 驅動），講不停的人不會 commit，只吐 Utterance 那條規則
永遠測不到。同理必須自己驅動 `voice_started/stopped`，否則 Chair 的軟插入會判定
「全場都沒人講」而在腳本角色講到一半就插話。

**接縫 2：音訊出口**（`speaker.LocalOutput` / `MutedOutput`）
`Chair` 只用 `Output` 的 `enqueue` / `end_of_utterance` / `is_busy` / `reset_marker` /
`first_audible_at` / `read()`。兩個替身都**繼承 `Output`**，只換「聲音往哪送」——
佇列、切幀、EOS 語意一行不改。

## 決定一：腳本模式一律不接 Discord

`discord_source.state_sync()` 會把頻道裡每個真人加進 `st.participants`。
**2026-09-05 實測**，同一份 `imbalance.json`：

| | 主席點名了誰 |
|---|---|
| 離線跑（無 Discord） | 「**Billis、達哥**，請各自說一個黑客松題目方向」← 對 |
| 接 Discord（有人在頻道裡聽） | 「**Alex Huang**，你對這兩點有什麼想法？」← 點到只是在聽的人 |

只因為頻道裡多了一個旁聽者，主席的注意力就轉到那個從頭到尾沒講話的人身上，
發言佔比也被稀釋，五分鐘後還會對他觸發「有人被冷落」。
**測試台的前提是「除了主席以外都是劇本」，接上 Discord 就守不住。**

## 決定二：三個執行模式

| 模式 | 判斷 LLM | 話術 LLM | TTS | 需要音訊裝置 | 用途 |
|---|---|---|---|---|---|
| `--mute` | ✅ | ✅ | **等長靜音** | ❌ | 無人值守、自動迭代、headless |
| 有聲（預設） | ✅ | ✅ | 真的 | ✅ | 人在旁邊聽，驗聲音與語速 |
| `--no-llm` | ❌ | ❌ | — | ❌ | 只測快路規則，零成本 |

⚠️ **靜音不能是「什麼都不做」。** Chair 的 `is_busy()`、冷卻期、`first_audible_at`
全靠音訊真的花時間排空。假 TTS 瞬間回空的話 `is_busy()` 立刻變 false，主席變成
「講完 0 秒就能再講」，`should_score` 的 busy 閘門形同虛設，慢路評分點的分佈整個變樣。
所以靜音要產**等長度**的靜音：`len(話術) ÷ replay.CHARS_PER_SECOND`（專案自己的語速
常數），格式與真 TTS 相同。

話術的 LLM 呼叫在 `--mute` 下**照跑**：那句話寫得好不好本來就是要測的，而且它用
`gpt-5.6-luna`，成本可忽略。省掉的只有 ElevenLabs。

## 決定三：`test` 檔位縮門檻，但只縮規則

沿用既有的 `style.py`（它本來就是在覆寫快路門檻），加一個 `test` 檔位。

**能縮**（純數字比較，走的是同一條 code path）：

| 常數 | 正式 | test |
|---|---|---|
| `OVERTIME_SECONDS` | 180 | 60 |
| `NEGLECTED_SECONDS` | 300 | 90 |
| `SILENCE_SECONDS` | 90 | 30 |

**不能縮**，因為跟不會跟著縮的東西耦合：

- `COOLDOWN_SECONDS` 30：主席講一句 TTS 要 8–11 秒（上限 50 字 ÷ 4.5 字/秒）。
  縮到 10 秒等於「講完 1 秒就能再講」，那是產品不會有的行為。
- `PAUSE_SECONDS` 1.0 / `ESCALATE_SECONDS` 15：跟 TTS 播放時間、LLM 往返
  （判斷 3.4s ＋ 話術 1.6s）耦合。縮了會讓「等不到停頓就升級」從例外變成常態。
- 慢路 `TICK` 5 秒：不縮的話，時間軸一壓縮，慢路在「每會議分鐘」看到的評分點就變少。

效果：全套約 50 分鐘 → 20–25 分鐘。**`test` 檔位不能取代 1× 的完整跑**——
每次發版前至少要有一場正式門檻的完整場次。

## 決定四：獨立場次套件 ＋ 一場三階段長會議

兩種測到的不是同一件事。

**獨立場次（回歸測試）**——決定性理由是**狀態污染**：

| 跨場景會殘留的狀態 | 效果 |
|---|---|
| `done: set[(類型, 對象)]` | 同一件事講過就不再講 |
| `st.room_silence_hits` | 全場沉默門檻每觸發一次 ×1.5 |
| `Chair._backoff_key` 退避 | 前一段的失敗壓住後一段的重試 |
| `st.interventions` 冷卻 | 前一段最後一次介入吃掉後一段開頭 30 秒 |

濃縮場次裡「某段沒抓到」可能不是判斷錯，是被前面吃掉了——**失敗歸因會非常難**。
獨立場次還可平行跑（總 wall-clock 更短）、可單跑一項、直接吻合 `score_run.py`
「一場會議＋一份 labels」的單位。

**一場長會議（整合測試）**——測得到獨立場次結構上測不到的：

1. 注意力分配：同時有兩件事該處理，仲裁規則選了哪一個
2. 冷卻期的排擠效應（這是產品行為，不是污染）
3. **階段偵測的正面驗證** ← `validation-results #7` 記載的已知缺口：
   「正面驗證仍缺一場真的走完三階段的錄音」。真實會議湊不到，**但劇本可以寫出來**。

⚠️ 長會議**不是把獨立劇本接起來**（長度會失控、開場暖身互相干擾），
是一份自己設計的 20–25 分鐘劇本，三階段各約 7 分鐘，介入時機由劇情帶出來。

### 涵蓋矩陣

| 反應 | 劇本 | 狀態 |
|---|---|---|
| 發言權失衡 | `imbalance` | ✅ 已驗（離線＋有聲各一次） |
| 發言超時（硬打斷＋earcon） | `overtime` | 待寫 |
| 全場沉默（＋退避） | `silence` | 待寫 |
| 有人被冷落 | `neglected` | 待寫 |
| 議程超時 | `agenda` | 待寫 |
| 離題 | `offtopic` | 待寫 |
| 僵局（爭執不下） | `deadlock` | 待寫 |
| 假共識 | `false_consensus` | 待寫 |
| 事實錯誤 ← **從未在真實會議觸發過** | `factual` | 待寫 |
| 收尾閉嘴 | `closing` | 待寫 |
| **該忍住**（負面測試，全程應 0 次） | `healthy` | 待寫 |
| 三階段（發散→呻吟區→收斂） | `full-meeting` | 待寫 |

軟插入等停頓、15 秒升級、30 秒冷卻不需要專屬劇本——上面每一場都會走到。

## 決定五：量化門檻用既有計分器

腳本場景有真實會議沒有的優勢：**真值是寫出來的，不是標出來的**。劇本說
「Alex 從 04:10 獨白到 08:20」，那個窗口就是 ground truth，不需人工標註。

所以階段 3 是把每個劇本的期望寫成 `labels.json` 的窗口格式
（見 `experiments/holdout/README.md`），直接餵 `experiments/score_run.py`——
**不寫第二套計分器**。

⚠️ 期望窗口要**從當下生效的門檻算**，不能寫死秒數。否則同一份劇本在 `test` 檔位與
正式檔位下「該介入的時間點」不一樣，兩次的分數就不能互相比較——那正是這整套要做到的事。

門檻等場景跑出實際分佈才定，現在不猜。定的時候套同一條紀律：**每組至少跑 5 次**
（`docs/evaluation.md`「單次測試會給出完全錯誤的結論」）。

## 執行順序

| # | 項目 | 為什麼是這個順序 |
|---|---|---|
| 1 | `--mute` 靜音模式 | 後面所有自動化的前提；headless 機器沒有音訊裝置 |
| 2 | `test` 檔位 | 讓每一輪驗證從 50 分鐘降到 20–25 分鐘 |
| 3 | Discord-free ＋ mute 實跑驗證 | 一次驗完 1、2 與已完成的 Discord-free |
| 4 | 其餘 10 個獨立劇本 | 涵蓋矩陣補滿 |
| 5 | 三階段長會議劇本 | 補上階段偵測的正面驗證缺口 |
| 6 | 量化門檻（labels ＋ score_run） | 要先有 4、5 的實際分佈才定得出來 |

## 不做什麼

- 不改 `Chair`、`fast_path`、`slow_path`、`Session` 的任何行為
- 不加速慢路與 Chair 的時序常數（見決定三）
- 不寫第二套計分器（見決定五）
- 不把這裡的分數當判斷品質的證據（見「它的定位」）
