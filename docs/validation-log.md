## 驗證 #1：ElevenLabs Scribe v2 Realtime 中文即時 STT

**日期**：2026-08-27　**結論**：✅ **可用，但有兩個必須處理的問題**

### 實測數字

素材：5.10 秒中英夾雜口語（sherpa-onnx 測試檔），`--realtime` 節流模擬真實會議。

| 指標 | 數字 |
|---|---|
| **尾段延遲（說完 → 最終文字）** | **0.34 秒** |
| 首次出字 | 2.78 秒（音訊進行中） |
| 部分轉錄更新頻率 | **約每 1 秒一次** |
| 批次 API 用量 | **約 1 credit ≈ 1 秒音訊** |

**0.34 秒這個數字很關鍵**：加上 earcon（零延遲）與 TTS 首字（~150ms），
整條「聽到 → 判斷 → 開口」的鏈路仍在可接受範圍內。
延遲不再是威脅——見 `interruption-design.md` 第五節的 earcon 策略。

**部分轉錄每秒更新** ⇒ 慢路評分**不必等 final**，可以邊聽邊評分。
這對「候選發言預先生成」是直接的支撐。

### 問題 1：中英夾雜會辨識錯 —— keyterms 可解（已驗證）

同一段音訊的對照：

| 設定 | 輸出 |
|---|---|
| 無 keyterms | 「与 **always**，**always** 是什么意思？」❌ |
| `--keyterms "OS" "作業系統"` | 「与 **OS**，**OS** 是什么意思？」✅ |

→ **會前設定檔裡的參與者姓名、專案名、技術詞，要自動轉成 keyterms 餵進去。**
這剛好接上既定設計：議題與名單本來就是會前用設定檔給的。

### 問題 2：輸出是簡體字

`language_code=zho` 仍輸出簡體。會議記錄要給台灣使用者看，需要後處理（opencc）
或尋找其他語言碼。**尚未解決。**

### 順帶確認

- **realtime 不回傳 `speaker_id`** —— 與官方說明一致（realtime 為低延遲省略 diarization）。
  diarization 靠音訊層解決（Discord 每人一軌／實體多麥），與原計畫相符，無需改動。
- 口語填充詞（「呃」）會被保留，對真實會議是好跡象。

### 值得注意的可用參數

實測與文件確認 Realtime WebSocket 支援這些，對本專案直接有用：

| 參數 | 用途 |
|---|---|
| `keyterms` | 專有名詞提示 ← **已驗證有效** |
| `commit_strategy` = `vad` / `manual` | 控制何時斷句 |
| `vad_threshold`、`vad_silence_threshold_secs` | **停頓偵測的控制點**——軟插入時機要用 |
| `min_speech_duration_ms`、`min_silence_duration_ms` | 同上 |
| `filter_background_audio` | 多人會議室降噪 |
| `no_verbatim` | 控制要不要保留填充詞 |

VAD 那幾個參數特別重要：`interruption-design.md` 說軟插入要「等停頓」，
**這就是那個停頓的來源**，不用自己做。

## 真實音訊鏈路：麥克風路徑已通（2026-08-28）

**結論**：✅ 音訊 → STT → `Utterance` 全鏈路驗證通過（本地麥克風）

```
✅ [0.7s→2.5s]   Alex：好，谢谢您吧。
✅ [10.5s→12.8s] Alex：继续讲完。
✅ [13.0s→21.1s] Alex：我继续说30秒。30秒太久了吧？...
```

⚠️ **但這條路不能取代 Discord**：單一麥克風收到的是混音，**無法區分說話者**——
而那正是當初選 Discord（每人一軌）的理由。麥克風路徑的用途是驗證鏈路，不是替代品。

### 五個踩過的坑（依性質分類）

| # | 問題 | 性質 | 修法 |
|---|---|---|---|
| 1 | **opus 解碼器沒載入** | macOS 環境 | `discord.opus.load_opus("/opt/homebrew/lib/libopus.0.dylib")` |
| 2 | **`voice_recv` keepalive 忙迴圈** | **上游 bug**（只在 Linux 測過） | monkey patch，見下 |
| 3 | commit 限流被踢線 | 本專案邏輯 | 送出 commit 後立刻重置狀態，不等回應 |
| 4 | 多個 bot 實例搶語音連線 | 操作 | 重啟前務必 `pkill` 乾淨 |
| 5 | **麥克風永遠不 commit** | 本專案設計漏洞 | 麥克風端加音量閘門，見下 |

**第 1 個最難查**：解不開封包時 callback 完全不觸發，**不拋任何錯誤**——
症狀是「bot 進得了頻道、看得到成員，但一個字都收不到」。

**第 2 個是真正的上游 bug**（`discord-ext-voice-recv`）：

```python
# 上游原始碼
vc._connection.socket.sendto(packet, (endpoint_ip, voice_port))  # macOS 拋 Errno 56
except Exception:
    ...
    continue          # ← 這條路徑沒有 sleep
else:
    time.sleep(self.delay)   # ← sleep 只在成功時執行
```

socket 已 connected，BSD 不允許 `sendto` 帶位址（Linux 允許，所以上游沒發現）。
例外分支漏了 sleep → **每秒重試上萬次、吃滿一顆核心、接收執行緒被餓死**。
實測 25 秒只收到 33 個封包（應有約 1250 個）。
修法：改用 `send()` 不帶位址，並補上退避。見 `discord_source.patch_keepalive_for_macos()`。

**第 5 個有普遍意義，值得記住**：

> **Discord 在人停止說話時會停止送封包；麥克風不會。**
> STT 層靠「一段時間收不到音訊」判斷句子結束並送 commit——
> 這個假設對 Discord 成立，對麥克風不成立（持續送靜音 → 永遠不逾時 → 永遠不 commit → 永遠不出字）。
> 麥克風端補上音量閘門（門檻 0.02，實測靜音約 0.002、說話約 0.25）後兩邊行為一致，順便省 API 額度。

### 「收到十幾個封包後斷流」根因：Discord DAVE 端對端加密（2026-08-28）

**症狀**：bot 連得上、`connected=True`、無任何錯誤訊息，但收到約 11 個封包後完全斷流。

**先前的誤判**：以為是「UDP 沒進來」，方向錯了。原本要跑的 `probe3.py` 三個判定分支
會一致導向錯誤結論——因為底層 callback 也會停，它會誤判成「網路／NAT 問題」。

**決定性線索藏在舊 log 裡**：`probe.log` 印的 `listening=...`，`...` 不是省略號，
是 `discord.utils.MISSING` 的 `repr`。`VoiceRecvClient.is_listening()` 的實作是
`return self._reader and self._reader.is_listening()`，所以那行代表
**第 5 秒時 `_reader` 已被 `stop_listening()` 拆掉**——不是收不到，是程式自己關掉了。

**完整根因鏈**（`probe5.py` 在 `stop_listening()` 上掛堆疊追蹤實測取得）：

```
環境裝了 davey 0.1.6
  → discord.py 在 voice IDENTIFY 送出 max_dave_protocol_version = 1
  → Discord 回 SESSION_DESCRIPTION：dave_protocol_version: 1（DAVE E2EE 開啟）
  → RTP payload 經傳輸層（aead_xchacha20_poly1305_rtpsize）解密後仍是 MLS 密文
  → discord-ext-voice-recv 不認識 DAVE，把密文直接餵給 opus 解碼器
  → OpusError('corrupted stream')
  → 例外從 PacketRouter._do_run 冒上來
  → PacketRouter.run() 的 finally 呼叫 voice_client.stop_listening()
  → 接收器永久拆除，之後的 UDP 封包全部無人接手
```

**實測數字**（`probe5.py`，30 秒）：

| 層 | 計數 | 說明 |
|---|---|---|
| UDP datagram | 466 | **封包一直有進來**，證明網路完全正常 |
| `AudioReader.callback` | 38 | 第 11 秒被移除監聽後凍結 |
| `PacketRouter.feed_rtp` | 2 | 第 2 個真實語音封包就炸了 |
| sink（解碼後） | 0 | 一個都沒出來 |
| 傳輸層 CryptoError | 0 | 傳輸層解密是成功的 |

**排除了什麼**：`repro_router.py` 離線餵 300 個合法 RTP 封包給 `PacketRouter`，
sink 收到 299 個、執行緒存活、`stop_listening` 零次 → 純解碼／路由路徑本身沒問題。

**修法**（`discord_source.py` 的 `patch_dave_receive()`，✅ 已實測驗證）：
在傳輸層解密之後、交給 opus 解碼器之前，補上 `dave_session.decrypt(user_id,
MediaType.audio, data)` 這一層。MLS session 的建立與 epoch 轉換由 discord.py
的 voice gateway 自行維護，我們只借用它已備妥的 `dave_session`。

**修正後實測**（`probe6.py`，30 秒）：

| 指標 | 修正前 | 修正後 |
|---|---|---|
| sink 收到封包 | 0 | **987**（≈19.7 秒 PCM） |
| reader 是否存活 | 第 11 秒被拆除 | **全程存活** |
| UDP → sink 通過率 | 0% | 93%（缺口是 RTCP 與靜音封包，屬正常） |

**閉環端到端驗證**（`python -m meeting_host.live`，Pi5 實跑）：

```
加入語音頻道：AGI 作戰指揮所 / Meeting Room
    監聽中：True｜頻道內：['Alex Huang']
    🎤 Alex Huang 音訊持續中：100 個封包（約 2.0 秒）
[00:04] Alex Huang：13，134。
```

**Discord 每人一軌帶身分 → STT → 逐字稿，整條鏈路首次跑通。**
專案唯一的擋路問題已排除。

**衍生缺陷（尚未修，需另外決定）**：上游把「單一封包解碼失敗」當成致命錯誤，
一個壞封包就永久拆掉整條接收路徑，且不留任何 user-facing 訊息。
即使 DAVE 修好，現場 demo 遇到任何封包損壞仍會整場靜默失效。

### 六項缺陷修正與評估證據重建（2026-08-28 下午）

第三方獨立審查的四項 ＋ 第一場真實會議抓到的兩項，全部先取證再修（各自一個 commit）：

| 缺陷 | 證據 | 修法 |
|---|---|---|
| STT 每次停頓後重連延遲翻倍 | 離線重現：ElevenLabs 靜音 **16 秒**送 close 1000 不帶訊息；`_fails` 永不歸零 → 2→4→8→30s | close 1000 且 `session_started` 過 → 立即重連；認證失敗（無 session）才退避。假 key 驗證退避仍在 |
| 慢路連噴 | 現場 06:34 起三連發 `type=無` | `should_score`（無新 utterance 跳過＋尊重快路冷卻）＋ `is_intervention`（`type=無` 不算） |
| replay 慢路只評一次 | 實跑：`score()` 呼叫 1 次 | 進迴圈每 TICK 用同一套規則；成本因跳過規則降到 ≈ utterance 數 |
| `--with-phase` 無作用 | `{phase_block}` 不在模板（grep=0）、場景無 `phase` | probe 改用產品 `build_prompt`；只有 `divergent_phase` 補 `phase`，其他不瞎填 |
| 兩套判定標準 | probe `threshold` vs 產品 `relative`，prompt 兩份手抄 | probe 直接 import `slow_path`；evaluation.md 標註規則統一為 `is_intervention()` |
| 24/24 無 assertion | probe 只印不比 | 比對 `expect` 的「該／不該」，輸出 TP/FP/FN/TN，exit code |

**「24/24」修正後的真相**：套上產品實際規則（`type=無` 否決）後，慢路單獨是 21/24——
三個 FN 全在 `overtime`，模型給 P4 但正確地回「無」，因為「發言超時」是快路的類型。
探針原本只量慢路，量錯了東西。改成量整個系統（快路 `check()` or 慢路）後：

```
8 場景 × 5 次 = 40 次   TP 30  FP 0  FN 0  TN 10   40/40   延遲中位 3.77s
```

**同日審查另外抓到並已修**：live 慢路 LLM 回來後沒重驗冷卻（TOCTOU）；
replay 以 `start` 揭露整句、比 live 早看到全文（改為講話中只給 `speaking` 訊號、`end` 才揭露）；
失敗重試語意 live／replay 不一致；`session_started` 應歸零退避計數。
**未採納**：「idle close 應立即重連」——實測靜音 16 秒就關，立即重連會在長停頓期間每 16 秒握手一次；
lazy 重連握手 0.21s、佇列撐 5s，三段逐字稿完整，遺失量 20ms 低於 STT 解析度。

### TTS 模型選擇（2026-08-29）：換成 `eleven_v3_conversational`

起因是使用者實聽回報「很像外國人在講中文」。查下去發現兩件事：

1. voice **Sarah** 是 ElevenLabs 英語語音庫的音色。它的 `verified_languages` 含 `zh`，
   但那只代表「講中文能聽懂」，不是中文母語音色。
2. **模型從來沒有被評估過。** `eleven_flash_v2_5` 是最初為了延遲選的，之後沒人回頭檢查。

**同音色（Sarah）、同一句話、只換模型的實測**（首位元組／總生成／語音長度）：

| 模型 | 首位元組 | 總生成 | 語音長度 |
|---|---|---|---|
| `eleven_flash_v2_5`（原本） | 0.19s | 0.49s | 8.8s |
| `eleven_turbo_v2_5` | 0.29s | 0.43s | 9.0s |
| `eleven_multilingual_v2` | 1.07s | 1.23s | 9.3s |
| `eleven_v3` | 0.70s | 4.07s | 9.8s |
| **`eleven_v3_conversational`（選定）** | **0.23s** | 1.43s | 9.4s |

**留在 flash 的延遲理由不成立**：v3_conversational 的首位元組只比 flash 多 40ms，人耳聽不出來。
總生成 1.43s 產出 9.4s 語音（即時的 6.6 倍），串流播放不會追不上——對我們只有首位元組重要。
最終由使用者實聽五個檔案選定 `eleven_v3_conversational`（中文聽感最佳）。

**v3 的已知限制對本專案無影響**：v3 不支援 SSML `<break>` 標籤，但主席話術全是純文字，
`src/` 與 `experiments/` 內沒有任何 `<break>`／`<phoneme>`（已 grep 確認）。

**還沒解的**：Sarah 仍是英語音色。使用者選定的 **Anna Su**（`r6qgCCGI7RWKXCagm158`，
verified `zh`／`taiwan mandarin`）是 Voice Library 音色，**免費方案不能透過 API 使用**
（HTTP 402 `Free users cannot use library voices via the API`），帳號內另一個中文音色 `Yu`
同樣被擋。要用真正的中文母語音色需要升級 ElevenLabs 方案。免費方案下 `verified_languages`
含 `zh` 的 premade 音色共九個（Sarah、Laura、Charlie、River、Will、Jessica、Brian、Lily、Bill），
都是英語語音庫音色，尚未逐一試聽。

### TTS 首位元組 2.44s 根因調查（2026-08-29）：連線建立與 `optimize_streaming_latency` 都已排除，2.44s 無法重現

先量測、後修正。用 `experiments/tts_probe.py` 新增的 `--bench` 分解模式，
在 Pi5（正式環境）與本機 Mac 各跑一輪，逐段量 DNS／TCP／TLS／伺服器 TTFB，
再對照「每次新開 `ClientSession`」（現況）vs「重用同一個 `ClientSession`」vs
`optimize_streaming_latency` 開／關。

**Phase 1：純連線握手分解**（不叫 TTS，`asyncio.open_connection` + `loop.start_tls`，n=10，單位 ms）：

| 環境 | DNS | TCP | TLS | 合計 |
|---|---|---|---|---|
| Mac（本機對照） | min 1 / med 1 / max 2 | min 5 / med 6 / max 6 | min 8 / med 8 / max 9 | min 13 / med 15 / max 17 |
| **Pi5（正式環境）** | min 3 / med 3 / max 89 | min 5 / med 6 / max 7 | min 9 / med 10 / max 11 | min 18 / med 19 / max 105 |

`ping api.elevenlabs.io` 從 Pi5 與 Mac 都只有 **2-3ms**（`34.8.184.191`，GCP anycast，離台灣很近的節點）。
DNS 偶爾有個位數次的高峰（89ms，疑似本地路由器上游解析冷快取），但握手全部落在
「幾十毫秒」量級，**連一次握手都湊不到 2.44 秒的 1/10**。

**Phase 2：實際打 TTS stream**（同一句「阿凱，你已經講了三分鐘，先讓其他人接一下。」，Pi5，`ttfb_total_ms`，單位 ms）：

| 條件 | n | min | med | max |
|---|---|---|---|---|
| 現況：每次新開 `ClientSession`（=目前 `speaker.py` 的行為） | 15 | 158 | 170 | 231 |
| 對照：重用同一個 `ClientSession` | 15 | 138 | 159 | 439 |
| `optimize_streaming_latency` 關（現況） | 10 | 139 | 155 | 345 |
| `optimize_streaming_latency=4` | 10 | 142 | 155 | 165 |

（另一輪 n=20、同句同環境的獨立重跑：min 157 / med 173 / max 396，方向一致。）

**結論：兩個候選都排除，2.44s 在今天（08-29）用完全相同的文字、程式路徑、Pi5 主機無法重現**：

- **連線建立不是主因**：`connect_ms`（TCP+TLS 合計）只佔 16-30ms，重用連線最多省下這 16-30ms
  （對照組中位數 159ms vs 現況 170ms，差距在雜訊範圍內，遠不到能解釋 2.4 秒的量級）。
- **`optimize_streaming_latency` 沒有可測得的效果**（開／關中位數都是 155ms）——查了 ElevenLabs
  現行 API 文件：這個參數已標示 **deprecated**，官方最新的 latency-optimization 指南完全沒提到它，
  只講 flash 系列模型＋WebSocket 在鄰近區域（含東南亞）預期 TTFB 是 **100-200ms**，
  跟這裡實測的 ~150-170ms 中位數一致。
- 整條鏈路（DNS + TCP + TLS + 伺服器合成 + 傳輸首位元組）**今天的中位數是 150-230ms**，
  完全落在設計預期 <1 秒之內，跟原本記錄的 2.44 秒差了一個數量級。
- 找不到任何一次重跑（Mac 10 次、Pi5 conn 10 次、Pi5 fresh 15+20 次、Pi5 reuse 15 次、
  Pi5 osl 10×2 次，共 100+ 次呼叫）落在秒級——連最極端的離群值（439ms、411ms）也只是
  平常的 2-3 倍，不是 2.44 秒的量級。

**UNVERIFIED：08-28 那次 2.44 秒具體是什麼造成的**——原始量測沒有留下 log（只留了寫進本文件的
兩個數字），事後無法回溯當時的網路狀態、ElevenLabs 服務端狀態，或是否與同一天大量其他探針
（STT realtime、Discord 語音接收等）搶佔了 Pi5 的網路／event loop。不排除是一次性的異常
（ISP 路由抖動、對方服務端排隊、或當時剛好撞上其他測試的並發），但**沒有證據支持這個猜測，
也沒有證據排除**——只能說「今天測不到」，不能說「知道當時為什麼」。

**裁決**：不修改 `speaker.py`。量測顯示現有的「每次新開 `ClientSession`」實作不是延遲主因，
`optimize_streaming_latency` 已被上游棄用且無效，沒有量測支持的候選可以動手修。
若未來真的實機再次觀察到秒級延遲，需要在**當下**用同一支探針量分解，而不是回頭猜這次的數字。

## 驗證 #3：介入評分的延遲與準確度

**日期**：2026-08-28　**工具**：`experiments/scoring_probe.py` ＋ `experiments/scenarios.py`

> **做法調整**：原訂「跑 thoughtful-agents 量延遲」。實際改成**直接測我們自己的三軸評分 prompt**——
> 因為我們本來就要改造評分準則（三軸／Key Rules／正反論證），照抄整個框架沒有意義，
> 真正要量的是「一次評分呼叫多久、判斷準不準」。
> 這同時是「逐字稿模擬測試」的雛形。

### 測試設計

8 個手寫場景，刻意埋入觸發條件；其中 **2 個是「不該介入」的對照組**（測誤報）。

### 第一輪結果（gpt-4o-mini，每場景 1 次）

| 場景 | 預期 | 實際 | 判定 |
|---|---|---|---|
| overtime | 該介入（超時） | 正向 P4/N2，類型抓對 | 部分對（**軸向錯**：超時應是負向） |
| silent | 該介入（正向） | 正向 P3/N2 [有人被冷落] | ✅ |
| offtopic | 該介入（負向） | 負向 P2/N3 [離題] | ✅ |
| false_consensus | 該介入（正向） | **不介入** P2/N1/None4 | ❌ **漏接 FN** |
| deadlock | 該介入（僵局） | 負向 N3，但類型答**「有人被冷落」** | ❌ **類型錯** |
| **healthy** | **不該介入** | **正向 P3/N2** | ❌ **誤報 FP** |
| **divergent_phase** | **不該介入** | **正向 P4/N2** | ❌ **誤報 FP** |
| mixed | 該介入 | 兩者皆有 [離題] | ✅（但只抓到離題，漏了超時） |

**F1 概況**：TP 4、FN 1、**FP 2**。

### 實測驗證了論文的預測：LLM 過度熱衷介入

**兩個「不該介入」的場景全部誤報**，而且 `divergent_phase`（發散期腦力激盪）拿到 **P4** 高分——
這正是 PTFA 失敗模式與 Kaner 呻吟區問題的具體重現。

> `prior-art.md` 發現 1 說「必須主動對抗 LLM 的介入偏差」——**這不是理論，第一輪就撞到了。**

### 一個可直接使用的診斷訊號

兩個 FP 場景有一個共同特徵：

```
type == "無"   但   positive >= 3
```

**模型自己說不出這屬於哪一類介入，卻仍然給高分要介入。**

→ **可直接當一條過濾規則**：類型為「無」時強制不介入。
這是零成本的 FP 抑制，優先於任何 prompt 調整。

### 延遲：中位 3.66 秒

| 統計 | 秒 |
|---|---|
| 中位 | 3.66 |
| 最快 | 3.34 |
| 最慢 | 6.32 |

**這個數字證實了快路／慢路分流的必要性**：3.66 秒對即時介入完全來不及，
慢路**必須**背景持續跑並預先備好候選發言，不能等到要介入時才算。

⚠️ **順帶浮現的成本問題**：若背景每 5 秒評分一次，一場 30 分鐘會議 ≈ **360 次呼叫**。
需要納入成本估算（見待辦）。

### 三模型對照（每場景 1 次）

| 場景 | 預期 | gpt-4o-mini | **gpt-4o** | gpt-5-mini |
|---|---|---|---|---|
| overtime | 負向・超時 | 正向 ⚠️軸向錯 | 負向 ⚠️類型錯 | 正向 ⚠️ |
| silent | 正向・冷落 | ✅ | ⚠️類型錯（答假共識） | 兩者皆有 |
| offtopic | 負向・離題 | ✅ | ✅ | 兩者皆有 |
| false_consensus | 正向・假共識 | ❌ **漏接** | 負向 ⚠️軸向錯 | 兩者皆有 |
| deadlock | 負向・僵局 | ⚠️類型錯 | ⚠️類型錯 | ⚠️類型錯 |
| **healthy** | **不介入** | ❌ FP | **✅ 唯一忍住** | ❌ FP |
| **divergent_phase** | **不介入** | ❌ FP | ❌ FP | ❌ FP |
| mixed | 該介入 | 兩者皆有 | ⚠️類型錯 | 兩者皆有 |

**延遲**：

| 模型 | 中位 | 最快 | 最慢 |
|---|---|---|---|
| gpt-4o-mini | 3.66s | 3.34s | 6.32s |
| **gpt-4o** | **4.42s** | 3.48s | 5.21s |
| gpt-5-mini | **13.74s** | 8.34s | 20.67s |

### 四個結論

**1. gpt-4o 最均衡，是目前唯一能忍住不介入的模型**

`healthy` 場景只有它給出「不介入」（P1/N1/None4）。這正是論文所說最難的能力。

**2. gpt-5-mini 不可用——它是論文描述的「OLMo7B 型崩壞」活標本**

8 個場景**全部**說要介入，其中 7 個是「兩者皆有」（P、N 同時 ≥3）。
Recall 接近 1、幾乎沒有 negative 判別力。再加上 13.74s 中位延遲，雙重出局。

> 這實測重現了 `prior-art.md` 發現 1 的兩極崩壞，也再次證明**模型選擇必須實測、不能假設**。

**3. ★ `divergent_phase` 三個模型 100% 誤報 → 階段感知不能靠 LLM 自己推斷**

三個模型都認為發散期的腦力激盪需要介入。**光靠 prompt 解不掉這個問題。**

> **設計結論**：Kaner 階段**必須是背景持續維護的狀態**（`interruption-design.md` C 類背景動作），
> 顯式餵進評分 prompt，而不是讓評分模型自己從逐字稿推斷。
> 這替「階段怎麼偵測」那個未解缺口確立了方向：**它是輸入，不是輸出。**

**4. 類型判斷是共同弱項，不能依賴**

`deadlock` 三個模型**全部**答「有人被冷落」——它們抓到「小婷 8 分鐘沒發言」這個表面訊號，
錯過真正的問題（同一爭點來回四輪）。`mixed`、`silent` 也有類似錯誤。

→ **介入類型應由快路規則判定，LLM 只負責「要不要介入」的強度評分。**

### 「type == 無」診斷訊號成立

三次出現「type 為無但仍要介入」，**三次都是 FP**（gpt-4o-mini 的 healthy 與 divergent、
gpt-5-mini 的 divergent）。而 gpt-4o 在 healthy 給 type=無 時就選擇不介入，判定一致。

→ **可直接當過濾規則：類型為「無」時強制不介入。** 零成本 FP 抑制。

### 5-1　核心發現：判斷與話術在同一次呼叫裡無法共存

**【commit】`573d74e`／`0087603`** — 同一批 34 點的四條件對照：

| 條件 | 帶逐字引號 | 介入次數 |
|---|---|---|
| 基準（現行單次呼叫） | 2/31 | 9 |
| 拿掉「≤2 句」「給下一步」限制 | 1/29 | — |
| 要求只講這場會議有的內容（v2） | 30/30 | **17** |
| 同一次呼叫另開 `notice` 欄位觀察逐字稿（v3） | notice **33/34** 正確／同次寫出的話術只有 **4/29** 保留引號、28/29 以「我聽到」開頭 | — |

v3 是決定性的：**模型看得見具體事實，寫話術時把它丟掉。**
v2 則證明話術指令會回頭污染判斷——只改話術指令、不動判斷指令，介入次數 9 → 17，
因為 pros/cons、三軸分數、話術本來就是同一份 JSON。

→ 拆成兩次呼叫：`score()` 只判斷（不含 utterance 欄位），
通過第一關閘門才呼叫 `phrase()` 寫那句話。

### 5-2　拆完之後的話術品質與延遲

**【commit】`0087603`**：34 點全部引用逐字稿，**32/34 逐字**，中位 36 字
（≈ 8.0 秒語音，短於先前的 8.9 秒），最長 54 字。
評分到排入佇列從 3.42s 變成 4.90s，一場這長度的會議多付 9 次呼叫。

**【產物】`experiments/out/two-call-2026-08-29-two-person/sweep.json`**
（8 個真實評分點 × 同一份 prompt，本節重算）：

| 話術 effort | 中位往返 | 最長 | 中位字數 | 帶引號 |
|---|---|---|---|---|
| **none** | **1.55s** | 1.78s | 36 | 8/8 |
| low | 3.47s | 5.49s | 36 | 8/8 |
| medium | 4.30s | **11.44s** | 37 | 8/8 |

三檔的引號率與字數量不出差異 ⇒ **選 `none`**。
「第二次呼叫可以慢一點貴一點」這個假設實際上用不到：話術呼叫卡在「決定要講」與
「排進 Chair」之間，Chair 的軟插入等不到停頓時 `ESCALATE_SECONDS=15s` 就升級成硬打斷，
多花的每一秒都從那 15 秒裡扣。

延遲差異在 0.2 秒內。硬上限訂 70 字（≈15.6 秒 = 軟插入升級門檻），
**超過整句作廢不截斷**——半句話比不講更糟。話術呼叫失敗則放棄這次介入，
**不退回罐頭句**（罐頭句正是這次要修掉的東西）。

### 5-3　`reasoning_effort` 是靈敏度旋鈕，不是品質旋鈕

**【commit】`ab9f2ee`**（部分執行：effort=low 跑了 4 輪，medium/high/xhigh 只有 probe）。
這個模型接受 `none/low/medium/high/xhigh`。從 `none` 調到 `low`：

- 穩定度幾乎不動：34 點中 16 個翻面 → 14 個
- 但**想講話的頻率大約三倍**：`is_intervention` `[6,12,8,7,12]` → `[25,23,18,22]`
- 多出來的介入**全部是「離題」、全部是同一句罐頭**

→ 推高 effort 不會讓判斷變準，只會讓它更常講同一句話。

### 5-4　三道「主席不該說話」的閘門

**收尾閘門**【commit】`4dee0e0`／`3206b54`：最近 90 秒出現 2 句以上道別用語即視為收尾。
8/29 那場錄音裡主席在大家道別後還「拉回議題」兩次；模型拿到完整逐字稿仍把道別判成離題，
所以改成確定性規則擋掉，不再問模型。兩個誤報消失，兩個機會窗格的 recall 維持 2/2；
標記詞在該錄音 t=634 之前一次都沒出現，閘門碰不到它不該碰的窗格。

快路那版有個結構性陷阱：直接用 `now` 當回看錨點，對「全場沉默」規則是**無效的**
——該規則在 `T_last + 90` 觸發，而收尾窗也是 90 秒，兩者互相抵消，
規則為真時閘門已經為假。必須把回看窗**錨定在最後有人講話的時刻**。
四條快路規則全部套用，因為它們的話術都預設會議還要繼續。

**失聰閘門**【commit】`5b7eaf8`：ElevenLabs 額度耗盡時 STT 與 TTS 同時死。
沒有人的靜默計數器停下來，五分鐘後主席開始逐一問每個人為什麼這麼安靜——四次，每次都播不出去。
Discord 的語音事件全程都在，只是沒有人讀。
失聰 = 兩條的 OR：STT 池回報全部串流離線（約 2 秒內抓到 auth／quota 失敗）
OR 距上一筆逐字稿累積的「有人在傳送」秒數 ≥ 45 秒（抓連著但不吐字的串流）。
累積量只在真的有人傳送時前進，所以**全場真的安靜不可能被誤判成失聰**。
**議程超時刻意不擋**：它純看時鐘，失聰時仍為真；全面噤聲會讓壞掉的主席跟克制的主席分不出來。

**話術生不出來就放棄**：見 5-2。

### 5-5　話術誠實性整批稽核

**【commit】`31f9c6c`**。主席對一位**講了全場 69%** 的人說「你從開會到現在還沒說話」。
根因：規則只知道「某人安靜了 N 秒」，話術卻斷言「從沒說過話」，而且 phrase bank 的 brief
把同一個假前提帶進每一個生成變體。四條規則的話術全部稽核過：

- 「有人被冷落」：只能宣告觸發條件真的檢查過的事
- 「全場沉默」第 3、4 變體預設「已討論出方向」「有討論可回顧」——全場零發言時是憑空捏造
- 「發言超時」分鐘數改 `floor`（下界宣告，不可多報）
- 「議程超時」改 `ceil`（上界宣告；`round(0.3)=0` 會講出「只剩 0 分鐘」）
- 系統 prompt 新增通則：**不可自行補上任何沒被告知的前提**

**議程門檻隨會議長度縮放**【commit】`6b4a150`：`AGENDA_WARN_SECONDS` 原本是絕對值，
5 分鐘的會議從第 0 秒就滿足「剩餘 ≤ 300」，開場第一個介入就是「議程只剩 5 分鐘」。
改成 `min(絕對上限, 會議長度/6)`——這正是 300s 這個常數在 30 分鐘預設值下隱含的比例，
所以 **≥30 分鐘的會議行為逐字不變**。

同一張單順手釘住了超時規則的回歸：把 8/29 錄音的 125 句逐字稿餵進「發言超時跨人累加」修正之前的
`_chain_start`，11 個誤報全部重現；餵進現行程式碼則是 0 個，
因為最長連續發言從 5.2 分鐘掉到 52.7 秒。

### 5-6　靜默術語提示卡（新能力）

**【commit】`ae7f75b`**。聽到沒人定義過的專有名詞就在觀戰 UI 印一張卡：
這場會議自己說過什麼、加上一句有出處的說明。**不經過 Chair、不出聲、不佔冷卻**，
所以時機判斷錯了也沒有代價。

防捏造是**結構性**的，不是靠 prompt 拜託模型：LLM 只回「候選詞」，
引言由程式從 `st.utterances` 逐字組出，逐字稿裡找不到的詞在查詢之前就被丟掉，
沒有來源連結的說明整段丟棄。

### 5-8　仍未解：判斷本身不穩（2026-08-31 重量）

**【產物】`experiments/out/rescore-twocall-2026-08-29-two-person/`**，
以拆呼叫後的兩次呼叫管線、同一批 34 點跑 5 輪：

```

admissible       [5, 1, 2, 4, 5]    範圍 1–5
逐點穩定         is_intervention 21/34、admissible 26/34
```

三軸自己的抖動：`negative` 有 29/34 個點在輪間變動、`none` 26/34、`positive` 20/34。
`margin = max(P,N) - None`，**22/34 個點至少有一輪 margin ∈ {0,1}**（動一分就翻面），
其中 3 個點每一輪都卡在一分之差。
第二個翻轉來源與三軸無關：`decide()` 判了介入卻被 `type=無` 擋掉（第 28、30 點）。

**判準線畫在比模型自己的解析度還細的地方。**

#### 多數決救不了（推導，非新增量測）

用上面 5 輪估每點介入機率 p̂，再算 k 票多數決後的每點機率
`q = P(Binomial(k, p) ≥ ⌈k/2⌉)`，總數變異數 `Σ q(1-q)`：

| 方案 | 預期介入數 | 標準差 |
|---|---|---|
| 單次（現況） | 6.00 | **1.62** |
| 3 票多數決 | 5.47 | **1.47** |
| 5 票多數決 | 5.18 | **1.36** |

三倍成本換 9% 離散度下降。原因：13 個搖擺點裡有 **7 個在 3 票之後 q 仍落在 0.2–0.8**
（p̂=0.4 → q=0.35，p̂=0.6 → q=0.65）。投票只能把「偶爾抽到怪值」推向邊緣；
這些點是模型**真的沒有穩定意見**。

而且觀測到的每輪總數變異數 5.00，大於各點獨立模型預測的 2.64（比值 1.89），
**有輪次層級偏移的跡象**——同一輪裡所有點會一起偏向介入或不介入。
若屬實，同時抽 k 次會彼此相關，投票效果比上表**更差**；上表是樂觀上界。
（此比較的 p̂ 來自同一批 5 輪，n=5，不是獨立檢定，只能當訊號。）

→ **這不是抽樣雜訊，不能靠平均掉。** 能動的方向是讓判準不要落在一分的差距上
（評分尺度／prompt），不是取樣策略。

#### 量測工具本身曾經失效（已修）

**【commit】`183ea62`**。拆呼叫之後 `score()` 不再回傳 `utterance`，
而 `rescore_slow_path.py` 仍只呼叫 `score()`，把 `None` 餵進單次呼叫時代的
`slow_result_admissible()`，導致閘門對每一點都回 `(False, "無話術")`。
在同一批 34 點上實測：**admissible 5 → 0**，理由分佈從
`{'': 30, 冷卻: 2, 收尾: 2}` 塌成 `{'': 25, 無話術: 9}`
——連冷卻與收尾的歸因都被覆寫，因為早退條件只涵蓋 `("type=無", "")`。
工具最後一次改動（15:01）早於拆呼叫（16:26）85 分鐘，從未對後拆版跑過，
兩份既有快取都還帶著拆呼叫前的話術，看起來完全正常。**這個 bug 不報錯。**

修正後工具鏡射 production 的兩次呼叫，快取帶 `pipeline="two-call"` 標記，
拆呼叫前的快取一律拒絕重算而不是硬算。

**缺鍵＝餵錯形狀，空字串＝模型沒寫出來**，把兩者合併正是這個 bug 靜默的原因。

⚠️ **舊的 `[6,12,8,7,12]` 不是被這個 bug 汙染的數字。**
`is_intervention()` 只讀 `verdict` 與 `type`，跟話術無關。

**沒有變體通過。** 粗尺度換來穩定但變瞎；明確判準改善 8/31 命中卻讓 8/29 掉命中、8/31 誤報升；兩段式命中不輸但誤報 3–5 倍。三者落在同一條 precision／recall 曲線上——把靈敏度調高，誤報就等比例升，沒有任何一個把標註的三個「該講」時刻與雜訊分開。

**未驗證的下一個假設**：判斷 prompt 只餵最近 6 句（`MeetingState.recent()`），而標註的三個時刻是「切斷別人後獨白 4 分鐘」「繞同一點」「滑到往事」——都是**跨越數分鐘**的形狀，6 句窗口看不見。要試的是時間窗口（如 3 分鐘）加結構統計（每人連續發言秒數、輪替次數、同一話題持續多久），不是再改指令。
