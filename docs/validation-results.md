## 各輪結論

### #1　即時中文 STT（2026-08-27）

ElevenLabs Scribe v2 Realtime 可用：尾段延遲 0.34 秒、首次出字 2.78 秒、部分轉錄約每秒更新。兩個必須處理的問題：中英夾雜辨識錯，以 keyterms 解決（已驗證）；輸出為簡體，以 OpenCC `s2twp` 後處理。
8/28 追查「收到十幾個封包後斷流」，根因是 Discord DAVE 端對端加密，`discord-ext-voice-recv` 不認識 DAVE 而把密文餵給解碼器；已繞過。

### #2　Pipecat 可行性（2026-08-27）

評估結論為「借骨架、自搭多人層」；其後實作全程自建（Discord → Scribe → 規則／LLM → TTS），未引入 Pipecat。

### #3　介入評分的延遲與準確度（2026-08-28）

8 個手寫場景各跑 5 次：系統層級 40/40、FP 0、延遲中位 3.77 秒。定案 `gpt-5.6-luna`、`reasoning_effort=none`、三軸相對比較（「不介入」軸有否決權）、`type=無` 為有效的「其實不用介入」訊號。
附錄：TTS 首位元組歷史數字 2.44 秒無法重現，Pi5 實測中位 150–230 毫秒。

### #4　Gemini Live 能否取代部分方案（2026-08-29）

不採用。首位元組 0.643 秒（含判斷）對比現行 TTS 0.17 秒（純唸稿）；輸入轉錄為簡體且出現語言汙染；多說話者場景無法區分誰在講。保留為「若之後重啟從這裡開始」的假設清單。

### #5　慢路拆兩次呼叫、四道閘門、話術誠實性（2026-08-31）

- **判斷與話術在同一次呼叫裡無法共存**：同次呼叫另開觀察欄位時 33/34 看對，寫出的話術卻只有 4/29 保留引號；只改話術指令會把介入次數從 9 推到 17。拆成兩次呼叫後 32/34 逐字引用，中位 36 字。
- 話術呼叫 `reasoning_effort=none`：三檔品質量不出差異，`none` 往返 1.55 秒、`medium` 最長 11.44 秒。
- 判斷用的 `reasoning_effort` 是靈敏度旋鈕不是品質旋鈕：`none`→`low` 穩定度幾乎不動，想開口的頻率約三倍，多出來的全是同一句離題罐頭。
- 三道「主席不該說話」的閘門：收尾（90 秒內 2 句道別）、失聰（STT 池全離線或有人傳送卻無逐字稿 ≥45 秒）、話術生不出來就放棄。
- 話術稽核：主席曾對講了全場 69% 的人說「你從開會到現在還沒說話」；四條規則的話術改為只宣告規則真的檢查過的事。
- 穩定度：拆呼叫前 5 輪 is_intervention [6, 12, 8, 7, 12]；拆後 [9, 3, 5, 7, 6]，13/34 點翻面，22/34 點至少一輪 margin ∈ {0, 1}。

### #6　第二份 holdout、兩個工具缺陷、雜務誤判（2026-09-01～02）

- 第二場真實會議（43 分鐘）作為 holdout #2，人工標註七個窗口。以錄到的介入計分：TP 3、FP 2、排除 3、opportunity recall 0.75。
- 重評工具的兩個缺陷由這份資料暴露並修正：`joined_at` 暫定值未被修正（silent 對帳 153 筆不符 → 0）；反事實把原始慢路疊上新結果而非替換（slow=14 = 5 + 9）。
- 現行 prompt 5 輪：admissible [4, 4, 8, 4, 6]；設備排解那個點 5/5 輪判離題；三處「該開口」慢路命中 [0, 0, 1, 0, 2]。
- 修正「會議雜務不算離題」後完整 5 輪：目標點 0/5，S1 誤報 [0×5]，admissible [2, 4, 6, 3, 4]；holdout #1 的閒聊窗口 5 輪全命中，admissible [3, 2, 5, 4, 4]。一處要盯：O1（獨白 4 分鐘）從 2/5 命中降到 0/5，5 次抽樣分不出是雜訊還是代價。
- 更正：8/31 尾段的語音活動是與會者離席後未掛斷的開麥，不是「有人講話卻不吐字」；該段適合當失聰偵測的反面測試。

### #7　階段自動判斷第一版（2026-09-02）

`phase.py`：每 60 秒把最近 150 秒逐字稿、輪替結構與慢路近期 type 分佈交給 LLM 判階段，連續兩次一致且信心 ≥ 0.6 才切換，切換後 120 秒內不再切；窗口內少於 3 次發言或只有一人說話時不判。預設只建議（`phase_suggestion` 事件），`--auto-phase apply` 才改 `Session.phase`。

反面驗證（`experiments/phase_replay.py`，兩場既有錄音的登記階段都是發散期）：
- 8/31（43 分鐘）：第一版在單人時段誤判呻吟區、無人說話的尾段以 0.99 信心判發散——加入「單人／空窗口不判」後 0 次切換。最終判準下：24 筆讀數（23 發散、1 筆單次的收斂讀數被遲滯擋下）、0 次切換、19 個時點拒判。
- 8/29（14.5 分鐘）：第一版在第 5–13 分鐘連續讀到呻吟區（信心 0.98），引用「我不要跟你開會」「氣死我了」「他就是在針對我」。在場者判定**不算拉鋸**——衝突的對象是主席與工具，不是議題。判準因此加上「衝突對象必須是議題本身；針對主席、AI、流程的不滿是對會議本身的評論」，並加入程式算的「主席在窗口內介入次數」訊號。改後 12 筆讀數全發散、0 次切換，模型的理由自己寫出「屬於對會議本身的評論，議題內容沒有推進」。

正面驗證（該切時會不會切）仍缺一場真的走完三階段的錄音。

## 方法

- 資料集：兩場真實 Discord 會議（14 與 43 分鐘）當 holdout，人工標註 opportunity／no_intervention 窗口；計分規則見 [experiments/holdout/README.md](../experiments/holdout/README.md)。
- 重評：`experiments/rescore_slow_path.py` 用現行 prompt 重跑每個慢路評分點，`--verify` 先以事件檔自帶的兩條不變量對帳重建。
- 穩定度：同一批點跑 5 輪，逐點看是否翻面；單次結果只當一個抽樣。
